Welcome back to my GSoC 2026 journey! In my [first blog post](/update/2026/06/25/week-1.html), I shared how we laid the foundational architecture for the browser-based execution sandbox and adaptive layout panels.

With those structural foundations in place, Phase 2 (Week 5 to 8) has been all about bringing the template playground to life. We implemented the core contract execution pipeline, refactored our UI for modularity, pivoted to dynamic template loading, built inline editor error reporting, etc.

Phase 2 was mainly about polishing the core features, adding new samples and enhancing the UI/UX of the application. Here is the weekly story of how Phase 2 unfolded.

## Key Accomplishments (Weeks 5-8)

### Week 5: Powering the Execution Engine (US-04, US-05, US-06)

My first goal for Phase 2 was to wire up the actual contract execution flow inside our hidden sandbox. This required implementing two main stages of a smart legal contract's lifecycle: initialization and triggering.

- **Contract Initialization (US-04)**: When a user clicks "Init Contract," the playground takes the compiled logic and passes the parameters to the Web Worker inside the sandbox. The worker executes `engine.init()`, establishing the contract's starting state, which is then stored in our global Zustand state. You can see the [init PR here](https://github.com/accordproject/template-playground/pull/935).
- **Contract Triggering (US-05)**: Once initialized, the user can write a JSON request payload (e.g., triggering a payment penalty or an agreement transition). Clicking "Send Request" passes the current state and the request to the worker, triggering `engine.trigger()`, which computes the output response, updates the contract state, and tracks emitted events. You can see the [trigger PR here](https://github.com/accordproject/template-playground/pull/936).
- **Execution Results UI (US-06)**: I built out the `ContractRunnerPanel` to capture these three output artifacts—the Response JSON, updated State JSON, and Event logs—and display them in side-by-side tabs. You can see the [execution results UI PR here](https://github.com/accordproject/template-playground/pull/939).

After thorough testing and polishing, we successfully merged this entire core execution pipeline!

### Week 6: Enhancing Modularity & Upstream Validation (US-07)

With execution working, Week 6 focused on code maintainability, modularity, and runtime payload safety.

- **Refactoring the UI**: The `ContractRunnerPanel` had grown into a monolithic file. To keep the codebase maintainable, I refactored and split it into smaller, stateful/stateless sub-components (such as isolated JSON editors and tab views), which improved state propagation and simplified the component tree. You can see the [UI refactor PR here](https://github.com/accordproject/template-playground/pull/946).
- **Concerto Payload Validation (US-07)**: In `template-engine`, we needed to ensure that logic payloads strictly match their Concerto models. After a discussion with the mentors, we decided that this change should be universal for all Accord libraries, thus should be implemented in Template-Engine. I updated the engine runtime to instantiate the Concerto Serializer during execution. This validates request and state inputs _before_ execution, and response and event outputs _after_ execution, throwing descriptive errors on type mismatches. You can see the [payload validation PR here](https://github.com/accordproject/template-engine/pull/164).
- **Downstream Dependency PR**: While working on the validation logic, I ran into a compilation error because the `Script` class from `cicero-core` was not exposed in its root index. I opened [PR #941 in `template-archive` (cicero)](https://github.com/accordproject/template-archive/pull/941) to export the `Script` type, which solved the downstream dependency typings.

### Week 7: Shareable Links & Usability Feedback (US-10)

Week 7 was marked by key feature completions, midterm evaluations, and developer-mentor collaboration:

- **GSoC Midterm Evaluation**: On July 10th, I officially passed my GSoC midterm evaluation! I really appreciate the feedback and guidance from my mentors. Their support has been a huge boost as we head into the second half of the project!
- **Shareable Links with Logic (US-10)**: I updated the URL share generator to compress and encode the logic editor's TypeScript code alongside the markdown and models. Loading a shareable link now seamlessly restores the custom logic state and opens the adaptive layout showing the logic panels. See the [Shareable Links with Logic PR here](https://github.com/accordproject/template-playground/pull/943).

He tested the new logic execution features and gave his valuable insights during the call. He asked crucial questions that helped us see the Playground from a real-user pov, not just as developers. We identified several usability enhancements, which became the main focus of Week 8.

### Week 8: Inline Error Diagnostics & Dynamic Templates (US-09)

This week, I focused on addressing the feedback from our Week 7 meeting, finalizing inline editor error reporting, and integrating dynamic library templates.

- **Inline Compilation Errors (US-09)**: In a text editor, compiling code only to see errors in a separate panel is frustrating. I mapped the compilation errors array from the Zustand store directly to Monaco editor markers. Now, syntax and compiler errors show up with red squiggly lines inline.
- **Problems Panel Navigation**: Clicking an error inside the lower `ProblemPanel` now calls a helper function that automatically focuses the Logic Editor, centers the screen and positions the cursor exactly at the line and column of the error.
- **The Dynamic Templates Pivot**: Initially, US-11, 12, and 13 called for hardcoding new templates (like a Late Payment Penalty and Service Agreement) directly into the playground. Thanks to my mentor **[Diana Lease](https://www.linkedin.com/in/dianalease/)** for submitting a PR #945 to implement dynamic template loading directly in the Playground. This utility downloads and decompresses `.cta` zip archives directly from the official Accord Project template library on the fly, rendering static local sample files obsolete. This PR will eventually get merged, allowing us to upload our new logic templates (which I had drafted locally) directly to the central registry instead of bundling them in the app. You can see this [dynamic template loading PR here](https://github.com/accordproject/template-playground/pull/945)

## Upstream Contributions & Discoveries

Contributing to the Accord Project means improving the wider ecosystem:

1.  **`template-archive` PR #941**: Exported `Script` type from `cicero-core` to enable downstream typing resolution. You can find the [PR here](https://github.com/accordproject/template-archive/pull/941).
2.  **`template-engine` PR #164**: Integrated Concerto payload serialization checks to validate input/output transaction structures at runtime. You can find the [PR here](https://github.com/accordproject/template-engine/pull/164).
3.  **`template-engine` PR #165 & Issue #163**: Strict validation check for `TemplateLogic`. Earlier in Phase 1, I noticed the engine compiled logic files even if the classes didn't extend the required `TemplateLogic` base class, so I opened [Issue #163](https://github.com/accordproject/template-engine/issues/163) to fix this. Two weeks ago, Rishabh Jain, a contributor to Accord Project, addressed this in [PR #165](https://github.com/accordproject/template-engine/pull/165), which sparked an interesting discussion: should this subclass check be an optional flag, or should we make it strict/unconditional for everyone? After a discussion with my mentor Matt Roberts and Rishabh, we eventually concluded that it's much safer to enforce this check unconditionally by default.

Healthy collaborations like these really help a community to grow!
