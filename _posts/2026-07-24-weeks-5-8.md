Welcome back to my GSoC 2026 journey! In my [first blog post](/update/2026/06/25/week-1.html), I shared how we laid the foundational architecture for the browser-based execution sandbox and adaptive layout panels.

With those structural foundations in place, Phase 2 (Week 5 to 8) has been all about bringing the template playground to life. We focused on three major areas: implementing the core contract execution pipeline, pivoting to a dynamic template library loading model, and integrating inline editor error diagnostics.

Here is the weekly story of how Month 2 unfolded.

---

## Key Accomplishments (Weeks 5-8)

### Week 5: Powering the Execution Engine (US-04, US-05, US-06)

My first goal for Month 2 was to wire up the actual contract execution flow inside our hidden sandbox. This required implementing two main stages of a smart legal contract's lifecycle: initialization and triggering.

- **Contract Initialization (US-04)**: When a user clicks "Init Contract," the playground takes the compiled logic and passes the parameters to the Web Worker inside the sandbox. The worker executes `engine.init()`, establishing the contract's starting state, which is then stored in our global Zustand state.
- **Contract Triggering (US-05)**: Once initialized, the user can write a JSON request payload (e.g., triggering a payment penalty or an agreement transition). Clicking "Send Request" passes the current state and the request to the worker, triggering `engine.trigger()`, which computes the output response, updates the contract state, and tracks emitted events.
- **Execution Results UI (US-06)**: I built out the `ContractRunnerPanel` to capture these three output artifacts—the Response JSON, updated State JSON, and Event logs—and display them in side-by-side tabs.

After thorough testing and polishing, we successfully merged this entire core execution pipeline!

---

### Week 6: Enhancing Modularity & Upstream Validation (US-07)

With execution working, Week 6 focused on code health, modularity, and runtime payload safety.

- **UI Componentization**: The `ContractRunnerPanel` had grown into a monolithic file. To keep the codebase maintainable, I refactored and split it into smaller, stateful/stateless sub-components (such as isolated JSON editors and tab views), which improved state propagation and simplified the component tree.
- **Concerto Payload Validation (US-07)**: In `template-engine`, we needed to ensure that logic payloads strictly match their Concerto models. I updated the engine runtime to instantiate the Concerto Serializer during execution. This validates request and state inputs _before_ execution, and response and event outputs _after_ execution, throwing descriptive errors on type mismatches.
- **Downstream Dependency PR**: While working on the validation logic, I ran into a compilation error because the `Script` class from `cicero-core` was not exposed in its root index. I opened [PR #941 in `template-archive` (cicero)](https://github.com/accordproject/template-archive/pull/941) to export the `Script` type, which solved the downstream dependency typings.

---

### Week 7: Shareable Links & The Dynamic Templates Pivot (US-10)

Week 7 was marked by a significant architectural pivot that changed how templates are managed in the playground.

- **Shareable Links with Logic (US-10)**: I updated the URL share generator to compress and encode the logic editor's TypeScript code alongside the markdown and models. Loading a shareable link now seamlessly restores the custom logic state and opens the adaptive layout showing the logic panels.
- **Usability Feedback Call**: I met with my mentors for a feedback call to review the new logic features. We identified several usability enhancements to make the playground more intuitive, which became the main focus of Week 8.
- **The Dynamic Templates Pivot**: Initially, US-11, 12, and 13 called for hardcoding new templates (like a Late Payment Penalty and Service Agreement) directly into the playground. However, my mentor Diana Lease submitted a PR (#945) implementing dynamic template library loading. This utility downloads and decompresses `.cta` zip archives directly from the official Accord Project library on the fly, rendering static local sample files obsolete. We decided to adopt this PR, allowing us to upload our new logic templates (which I had drafted locally) directly to the central registry instead of bundling them in the app.

---

### Week 8: Inline Error Diagnostics & UI Usability (US-09)

This week, I focused on addressing the feedback from our Week 7 meeting and finalizing inline editor error reporting.

- **Inline Compilation Errors (US-09)**: In a text editor, compiling code only to see errors in a separate panel is frustrating. I mapped the compilation errors array from the Zustand store directly to Monaco editor markers. Now, syntax and compiler errors show up with red squiggly lines inline.
- **Problems Panel Navigation**: Clicking an error inside the lower `ProblemPanel` now calls a helper function that automatically focuses the Logic Editor, centers the screen, and positions the cursor exactly at the line and column of the error.
- **Solving Async Debounce Race Conditions**: With dynamic recompilation running in the background, fast typing could trigger overlapping compilation calls, causing race conditions and UI locks. I resolved this by writing a custom `asyncDebounce` utility that correctly groups and isolates resolving promises.

## Challenges Faced

One of the main challenges this month was resolving asynchronous race conditions in our state store. During typing, background logic compilation runs on a debounce. However, standard debouncing does not account for asynchronous resolution, meaning slow network fetches or heavy worker tasks could resolve in the wrong order. Creating a custom `asyncDebounce` that isolates execution promise cohorts was key to ensuring the UI stays responsive and error-free.
